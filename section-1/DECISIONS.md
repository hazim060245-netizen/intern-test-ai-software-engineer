# บันทึกการตัดสินใจทางสถาปัตยกรรม (DECISIONS.md)

เอกสารนี้บันทึก 5 การตัดสินใจสำคัญในการออกแบบและพัฒนาตามข้อกำหนด 1.2

---

## D1: การจัดการ State การเข้าสู่ระบบและสิทธิ์ผู้ใช้ใน React (ส่วนที่ 3)
- **ทางเลือกที่คิดไว้:** (A) React Context API + LocalStorage  (B) Redux Toolkit  (C) Zustand
- **เลือก:** A
- **เพราะ:** ข้อมูลที่ต้องแชร์ข้ามหน้ามีเพียงข้อมูลผู้ใช้ที่ล็อกอิน (User Object, Role, Mock JWT Token) และข้อความแจ้งเตือน Flash Alert เมื่อเกิด Route Guard Redirect การใช้ React Context ร่วมกับ LocalStorage ตอบโจทย์ครบถ้วนโดยไม่ต้องเพิ่ม External Dependency ทำให้โปรเจกต์เบา รันง่าย และเข้าใจโค้ดได้ทันที
- **ข้อเสียของ A ที่ยอมรับ:** หากในอนาคตระบบขยายตัวจนมี State ขนาดใหญ่และมีความถี่ในการแก้ไขสูง Component ทั้งหมดใต้ Provider อาจ Re-render ซ้ำซ้อน ซึ่งในอนาคตสามารถแยก Context ให้เจาะจงขึ้น หรือย้ายไปใช้ Zustand/Redux Toolkit ได้

---

## D2: การออกแบบสถาปัตยกรรม Route Guard เพื่อป้องกันการเข้าถึงข้ามสิทธิ์ (ส่วนที่ 3)
- **ทางเลือกที่คิดไว้:** (A) Higher-Order Component (HOC)  (B) Dedicated Wrapper Component (`<ProtectedRoute>`)  (C) ตรวจสอบเงื่อนไขใน `useEffect` แยกเป็นรายหน้า
- **เลือก:** B
- **เพราะ:** การใช้ Wrapper Component ครอบ Route ใน `App.jsx` (เช่น `<ProtectedRoute requiredRole="admin">`) ทำให้อ่านโครงสร้างสิทธิ์ทั้งหมดได้ชัดเจนจากศูนย์กลาง (Single Source of Truth) จัดการทั้ง 3 กรณีตามโจทย์ได้อย่างสมบูรณ์ (ไม่ได้ล็อกอินส่งไป `/login`, เข้าผิด Role ส่งกลับหน้าตนเองพร้อม Flash Alert, สิทธิ์ถูกต้องเปิดให้ใช้งาน)
- **ข้อเสียของ B ที่ยอมรับ:** Route Guard ฝั่ง Frontend เป็นเพียงการควบคุมระดับการแสดงผล (UI Layer) เพื่อสร้าง UX ที่ดีเท่านั้น โดยตัวระบบยังต้องมี Middleware ตรวจสอบสิทธิ์ในระดับ API/Backend เสมอ (Defense-in-depth)

---

## D3: การกำหนด Data Type และ Constraint สำหรับสถานะของ Task (ส่วนที่ 2)
- **ทางเลือกที่คิดไว้:** (A) `VARCHAR` ร่วมกับ `CHECK Constraint`  (B) PostgreSQL `ENUM Type`  (C) แยกตาราง `task_statuses` (Lookup Table)
- **เลือก:** B (ร่วมกับ CHECK Constraint เพื่อความปลอดภัยสูงสุด)
- **เพราะ:** สถานะของระบบถูกกำหนดตายตัวไว้เพียง 2 สถานะคือ `'To Do'` และ `'Done'` การใช้ PostgreSQL ENUM (`CREATE TYPE task_status AS ENUM ('To Do', 'Done')`) ใช้พื้นที่จัดเก็บเพียง 4 ไบต์ต่อแถว เปรียบเทียบข้อมูลได้เร็วกว่า String ธรรมดา และป้องกันข้อมูลผิดพลาดในระดับ Engine ของฐานข้อมูลโดยตรง
- **ข้อเสียของ B ที่ยอมรับ:** หากในอนาคตต้องการเพิ่มสถานะใหม่ (เช่น In Progress) จะต้องรันคำสั่ง `ALTER TYPE ... ADD VALUE` ซึ่งอาจยืดหยุ่นน้อยกว่า Lookup Table แต่สำหรับความต้องการที่สถานะตายตัว ทางเลือกนี้มีประสิทธิภาพและเสถียรที่สุด

---

## D4: กลยุทธ์การอัปเดต UI เมื่อ Employee เปลี่ยนสถานะเป็น Done (ส่วนที่ 3 และ 4)
- **ทางเลือกที่คิดไว้:** (A) Optimistic UI Update แบบ Immutable พร้อมบันทึก Snapshot ไว้ Rollback เมื่อ Server ล้มเหลว  (B) รอการตอบกลับจาก Server ให้สำเร็จก่อนจึงเปลี่ยนสถานะบนหน้าจอ (Pessimistic Update)  (C) สั่ง Polling ดึงข้อมูลใหม่ทั้งชุดหลังคลิกปุ่ม
- **เลือก:** A
- **เพราะ:** ให้ประสบการณ์การใช้งาน (UX) ที่รวดเร็วทันใจ สถานะเปลี่ยนเป็น Done ทันทีที่คลิกโดยไม่รู้สึกกระตุกจาก Network Latency ขณะเดียวกันก็ตรงตามกฎของโจทย์ข้อ 4 ที่ว่า *"ถ้า server บันทึกไม่สำเร็จ หน้าจอต้องไม่โชว์ว่า Done"* โดยเมื่อเกิดข้อผิดพลาด ระบบจะ Rollback คืนค่า Snapshot เดิมและแสดง Error Alert ทันที
- **ข้อเสียของ A ที่ยอมรับ:** จำเป็นต้องจัดการ State ซับซ้อนกว่าปกติ โดยต้องดูแลทั้งขั้นตอนจำลองการเปลี่ยนแปลง และขั้นตอนการคืนค่าเดิมเมื่อเกิด Error

## D5: การออกแบบ Composite Index บนตาราง tasks สำหรับรองรับงานของ Employee (ส่วนที่ 2)
- **ทางเลือกที่คิดไว้:** (A) สร้าง Single Index บนคอลัมน์ `assigned_to`  (B) สร้าง Composite Index `(assigned_to, created_at DESC)`  (C) ไม่สร้าง Index เพราะมองว่าตารางมีขนาดเล็ก
- **เลือก:** B
- **เพราะ:** Query หลักของพนักงานคือการดึงเฉพาะงานของตนเองและเรียงลำดับจากสร้างล่าสุดไปเก่าสุด (`WHERE assigned_to = $1 ORDER BY created_at DESC`) การใช้ Composite Index ทำให้ฐานข้อมูลค้นหาและเรียงลำดับผ่าน Index Tree ได้โดยตรง ไม่ต้องเสียเวลาทำ Sorting ในหน่วยความจำ (Index Scan / Avoiding Filesort)
- **ข้อเสียของ B ที่ยอมรับ:** Composite Index ใช้พื้นที่จัดเก็บและมี Overhead เล็กน้อยขณะทำการ `INSERT`/`UPDATE` งานใหม่ แต่เมื่อเทียบกับความเร็วในการอ่าน (Read Query Performance) ถือว่าคุ้มค่าอย่างยิ่ง
